  Deviations from the Generic UML (Facade + State)

1. States have more than nextState()
   The Class Diagram already gives them these (e.g. InProgress: paused, failed, exception).
   nextState() alone allows only one way out of a state. The only alternatives are
   if/else or switch chains (banned) or removing pause/fail/escalation.
   The base WorkItemState also declares them, so WorkItem can call them without type checks.

2. WorkItem passes each of these calls on to its state.

3. Extra helpers:
   - isWithinDeadline() and notifyWorkflow(): the State Diagram's guard and action
   - hasValidData(): used by Validation
   - addTimeSpent(): records time for the deadline
   - id, name, getName(), getStateName(): lookup and printing

4. AbstractWorkItem's state and mediator are protected, not private,
   because WorkItem's getState()/setState() need them.

5. WorkItem deletes its old state on every change (composition, not aggregation).

6. TIVIDY owns the WorkflowMediator.

7. WorkflowMediator is a stub: it only stores the work items, and notify() is empty.

8. The State Diagram and Sequence Diagram 1 disagree with the Class Diagram.
   The code follows the Class Diagram, so those two diagrams need updating.

Facade operations

TIVIDY only has what a user does: createWorkItem, advanceWork, submitWork,
pauseWork, resumeWork, printStatus.
Fail, exception, retry and validate are triggered by the engine (Mediator / escalation),
not the user, so they are left out of the facade.
createIterator() lets clients (e.g. the web UI) walk the work items without seeing how they are stored.

Ownership and lifetime rules (creation / deletion)

- TIVIDY owns the WorkflowMediator and the Creator. The Mediator owns every work item and deletes them.
- Factory Method: TIVIDY creates every work item through Creator::createWorkItem(id, name, deadline, mediator),
  so factoryMethod() now takes the item's details instead of always making the same item.
- Chain of Responsibility: the UML shows composition, so each handler owns its successor and deletes it.
  Successors must be created with new. Replacing a successor deletes the old one, and a successor that
  would make the chain loop is rejected.
- Observer: a handler watches one work item at a time. Attaching it elsewhere moves it, and whichever of
  the two is destroyed first detaches from the other, so neither is left pointing at a deleted object.
- Composite: the UML shows aggregation, so a group does not own or delete its children. This lets a
  group hold work items that the Mediator owns.
- Decorator: a decorator wraps a component without owning it, so the component must outlive its decorators.
- Classes that own objects (work items, Mediator, Memento, Caretaker, handlers) cannot be copied,
  because a copy would delete the same objects twice.

How the patterns connect (Mediator as the hub, as in the UML)

- TIVIDY (Facade) only talks to the WorkflowMediator and the Creator. New facade operations so a client can
  reach the rest of the flow: logTime(), addTask(), setStrategy(), saveAsTemplate(), createFromTemplate().
- WorkflowMediator now holds what the UML links it to:
  - TaskEscalationManager: every work item it registers gets a "Team lead -> Manager" escalation chain
    attached as its observer. The Mediator owns these chains.
  - Strategy: when an item completes, the Mediator scores its tasks with the current strategy
    (average by default). setStrategy() replaces it and the Mediator deletes the old one.
  - Target/Adapter: when an item completes, the Mediator notifies the external system through the Adapter.
  - PrototypeManager: stores template work items. createFromPrototype() clones one into a new work item.
- Observer + Chain of Responsibility: the handler sends how many time units the item is past its deadline
  (0 if on time). On time = not escalated; under 3 = team lead; under 7 = manager; more = unhandled.
  Logging time also notifies observers, so an item escalates as soon as it goes overdue.
- Prototype: AbstractWorkItem has clone(id, mediator). A clone keeps the name, deadline and tasks but gets
  a new id, starts in Created and has no observers, data or time logged.
- Memento, Composite and Decorator are used by the client around work items (as in the UML), not through the facade.
