  Deviations from the Generic UML (Facade + State)

1. States have more than nextState()
   The Class Diagram already gives them these (e.g. InProgress: paused, failed, exception).
   nextState() alone allows only one way out of a state. The only alternatives are
   if/else or switch chains (banned) or removing pause/fail/escalation.
   The base WorkItemState also declares them, so WorkItem can call them without type checks.

2. WorkItem passes each of these calls on to its state.

3. Extra helpers:
   - isWithinDeadline() and notifyWorkflow(): the State Diagram's guard and action
   - hasValidData(): used by Validation
   - addTimeSpent(): records time for the deadline
   - id, name, getName(), getStateName(): lookup and printing

4. AbstractWorkItem's state and mediator are protected, not private,
   because WorkItem's getState()/setState() need them.

5. WorkItem deletes its old state on every change (composition, not aggregation).

6. TIVIDY owns the WorkflowMediator.

7. WorkflowMediator is a stub: it only stores the work items, and notify() is empty.

8. The State Diagram and Sequence Diagram 1 disagree with the Class Diagram.
   The code follows the Class Diagram, so those two diagrams need updating.

Facade operations

TIVIDY only has what a user does: createWorkItem, advanceWork, submitWork,
pauseWork, resumeWork, printStatus.
Fail, exception, retry and validate are triggered by the engine (Mediator / escalation),
not the user, so they are left out of the facade.

Deviations from the generic UML diagram (Strategy + Memento + Chain of Responsibility)

Strategy:
 - No deviations the code was implemented identical to the UML class diagram

Memento:
 - Caretaker Implementation: In the generic UML diagram, Caretaker is modeled without attributes or methods. In C++, the attribute std::vector<WorkItemMemento*> and the functions addMemento(), getMemento(), and a cleanup destructor were added so the class can store and retrieve snapshots.

Chain of Responsibility:
  - There is no handler class, so I changed successor from being of type Handler to TaskEscalationManager.
  - I also changed successor to be a protected member instead of private so that the handlers have access to it.
  - I also added a function setSuccessor() that allows us to set the successor of a handler.

Deviations from generic UML diagram (Decorator + Abstract Factory + Observer)

Decorator:
- Added in a component class and kept WorkItem as a concreteComponent. Also Decorator itself should inherit from Component and WorkItem should also inherit from Component. 


Observer:
- Removed attach/detach/notify from Mediator. Subject is AbstractWorkItem, concreteSubject is WOrkItem

Abstract Factory:
- Removed relationship with Mediator cause its forcing a relationship. What is mediator coordinating here? Added a relationship with TIVIDY(Facade) so the Facade can use runWorkflow to create an instance of a workflow from either Factory 1 or Factory 2. The Mediator already has a responsibility and thats to coordinate the AbstractWorkItem objects. So giving Factory to Facade provides a simple interface for the Client to use.
